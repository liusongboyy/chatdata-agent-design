# 问数质量分析：按问题类型看质量

- Status: Draft
- Date: 2026-11-04
- Related: `.scratch/health-dashboard/spec.md`、`ask_audit_log`、`FailureClassifier`

## 1. 要解决什么

健康度看板已经能看到「整体成功率」和「失败原因排行」，但**看不出哪类问题难**：

```
保险分析域最近 30 天：
  客户总数是多少？           39 次，失败 20 次 → 51%
  按险种类型统计保单数量      39 次，失败  0 次 → 0%
  按大区统计保单数量          40 次，失败  0 次 → 0%
```

三个问题看起来都是「问一个数」，但「客户总数」有一半失败。**只看总量看不出这个**——
整体失败率 9% 会被大量成功掩盖，而某个高频问法已经坏了一半。

**这一页回答**：哪类问题在拖后腿、具体是哪个问法。

## 2. 目标与非目标

**目标**：按**问题结构**分组统计成功率与耗时，找出「某类问题系统性不好用」。

**非目标**：
- **不做语义聚类**。不把「客户总数」「客户有多少人」归成一类——那是
  embedding 或 LLM 的活，成本高且不稳定。这一期用**确定性规则**。
- **不做逐条问题追踪**。已有审计表可查，这里做的是聚合视图。
- **不给优化建议**。同健康度看板的理由：改哪一条是业务判断。

## 3. 数据现实（已核实）

| 项 | 实测 |
|---|---|
| 30 天审计行数 | 6698 |
| 有简化 DSL | 4878 |
| 有完整 DSL | 9 |
| 没有 DSL | 1811（绝大多数是失败，DSL 没生成出来） |

**简化 DSL 结构**（占绝大多数）：
```json
{"metric":"保费合计","dimension":"大区","time":"全部","filter":""}
```

**完整 DSL** 是 `AskDsl` 的序列化（`metrics[]` / `dimensions[]` / `filters[]`…）。

设计必须**同时兼容两种结构**，且**容忍没有 DSL 的行**——
1811 条没 DSL 的恰恰全是最该看的失败。

## 4. 分类规则

有 DSL 时按**结构**分，没有时按**问题文本**兜底。

### 4.1 有 DSL：按结构

| 判据（依次匹配，命中即止） | 类型 | 为什么这是有意义的一类 |
|---|---|---|
| `dimension` / `dimensions` 非空 | **分组统计** | 「按大区统计」——维度解析与分组 |
| `filter` / `filters` 非空 | **带筛选的单值** | 「华东的保费是多少」——筛选 + 聚合 |
| 其余 | **单值汇总** | 「总数是多少」——最简单，失败通常意味着指标没配 |

**判据必须用 JSON 函数取字段值，不能用 `LIKE`。**
实测踩过：`dsl_json LIKE '%"dimension":"%'` 会把 `"dimension":""`
（空串）也算成"有维度"，于是 4878 条全被归进「分组统计」。
必须 `JSON_UNQUOTE(JSON_EXTRACT(...)) <> ''`。

**实测分布**（最近 30 天 6698 行）：

| 类型 | 条数 | 失败 |
|---|---|---|
| 分组统计 | 2620 | 13 |
| 单值汇总 | 2267 | 27 |
| 未分类（无 DSL + 关键词兜底也认不出） | 1203 | **200** |
| 分组（关键词兜底） | 534 | 27 |
| 归因 / 趋势 / 对比 | 74 | 0 |

**「未分类」里 200 条失败**，占全部失败的 6 成——正是这一页该让人看见的东西。
它的总量占 18%，接近但还没超 20% 的警戒线。

### 4.2 没有 DSL：按问题文本

1811 条没有 DSL，其中大部分是失败。这些行**不能丢**——
丢了就看不到"哪类问题连 DSL 都生成不出来"。

按关键词粗分（只做兜底，不追求精确）：

| 关键词 | 类型 |
|---|---|
| 为什么 / 原因 / 分析 | 归因分析 |
| 走势 / 趋势 / 变化 | 趋势 |
| 同比 / 环比 / 对比 | 对比 |
| 按 / 各 / 分 | 分组 |
| 其他 | **未分类** |

**「未分类」这个桶本身是个信号**：它持续变大说明有新的问法模式规则没覆盖。

## 5. 页面设计

### 5.1 顶部：按类型的总览

```
问题类型                              最近 30 天

类型          提问    成功率    平均耗时    典型问题
────────────────────────────────────────────────────
带筛选单值     412     72.3%     1.8s       「华东的保费是多少」
单值汇总      2,105    91.2%     1.4s       「客户总数是多少」   ← 51% 失败的那个在这里
分组统计      1,831    99.1%     1.6s       「按大区统计保单数量」
时间序列        83    100.0%     1.3s       「各月份保费走势」
未分类        1,205    88.0%     1.7s       —
```

**「典型问题」列很有用**：一个类型叫什么名字是抽象的，
但看到「客户总数是多少 51% 失败」立刻就知道该查什么。

### 5.2 下部：某类型里的高频问法

点开一个类型，列出这个类型下**提问次数最多的问法**及其成功率：

```
单值汇总 · 2,105 次

问法                          次数   失败   成功率   平均耗时
客户总数是多少                  39     20    48.7%    1.4s   ← 明显异常
保单总数是多少                  41      0   100.0%    1.2s
按保单状态统计保单数量            40      0   100.0%    0.8s
...
```

**按次数排序而不是按失败率**：只出现一次且失败的问题没有统计意义，
而出现 39 次失败 20 次的才是真的在影响用户。

### 5.3 一个刻意的限制：不显示样本少于 N 的问法

```
N = 5
```

样本太少时成功率是噪声。显示出来会让管理员去追一个偶然现象，
而真正的问题被稀释。

## 6. 实现

### 6.1 后端

`GET /api/engine/admin/health/quality?days=30&minSamples=5`

```java
record QualityReport(
    List<TypeStat> types,          // 按类型汇总
    Map<String, List<QuestionStat>> questionsByType
)

record TypeStat(String key, String label, long asks, long failures,
                double successRate, long avgMs, String sampleQuestion)

record QuestionStat(String question, long asks, long failures,
                    double successRate, long avgMs)
```

**分类器是纯函数**，与 `FailureClassifier` 同样的做法：从真实数据提炼规则，
写测试锁住。

### 6.2 前端

健康度页面加第二个标签页（「质量分析」），不新开路由——
两个视图回答的是同一类问题（这个系统好不好），分开放反而要来回切。

## 7. 验收

1. **保险分析域**：能看到「客户总数是多少」39 次 / 51% 失败这个真实异常
2. **分类覆盖率**：有 DSL 的行 100% 落在前四类里，没有的行落在兜底类
3. **未分类桶**：小于总数的 20%（超过说明规则不够用）
4. **样本阈值**：少于 5 次的问法不显示
5. **没有 DSL 的行不丢**：它们计入类型统计，只是归到兜底类
6. **空库不崩**：返回全零而不是 500

## 8. 风险

| 风险 | 应对 |
|---|---|
| 关键词分类不准 | 只用于**没有 DSL** 的兜底；有 DSL 的一律按结构分 |
| 「未分类」越来越大 | 把它当信号而不是垃圾桶：超过 20% 就该提炼新规则 |
| 问题文本相近但被算成不同问法 | 这一期接受。语义聚类是独立工程，不混进来 |
| 耗时统计受模型波动影响 | 显示中位数而非平均值（待定，见下） |

### 待定：平均耗时还是中位数

平均值会被少数超时拉高。中位数更能代表"典型体验"。
但 MyBatis 里算中位数要单独查一次。

**倾向中位数**——这一页的目的是"看典型情况"，平均值容易被一个 180 秒超时污染。

## 9. 不做

- 语义聚类 / 相似问法归并
- 逐条问题追踪（审计表已有）
- 自动推荐建模修复
- 跨域对比（域之间问题模式差异太大，放一起没有意义）
