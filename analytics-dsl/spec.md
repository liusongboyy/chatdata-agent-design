# DSL 补排序 / Top-N、占比、同环比

- Status: Done（2026-10-26）
- Date: 2026-10-26
- Related: `.scratch/derived-metrics/spec.md`（指标之间的运算）、`docs/adr/0002`（权限执行点）

## 1. 要解决什么

评测里三类问题一直答不了，且都**不会报错、只是答案不对**：

| 问法 | 缺的表达 | 之前的表现 |
|---|---|---|
| 「保费最高的 3 个区域」 | 排序 + 截断 | 返回全部区域 |
| 「各区域保费占比」 | 相对总量的比值 | 只能给绝对值，用户自己算 |
| 「2025 年保费同比增长多少」 | 两个时间窗的对比 | 只查本期，或干脆不理解 |

## 2. DSL 的三个新字段

```json
{
  "metrics": ["保费"],
  "dimensions": ["区域"],
  "sort": [{"field": "保费", "direction": "desc"}],
  "limit": 3,
  "shareOf": ["保费"],
  "compare": "yoy"
}
```

- `sort[].field` 是**输出列名**（指标、维度，或系统生成的「保费占比」「保费同比」），
  不是物理列名——占比、同比这些列在 DSL 里没有对应字段。
- `limit` 只能**收紧**系统上限（1000），不能突破。
- `shareOf` 必须是 `metrics` 里已有的名字。
- `compare` 只接受 `yoy` / `mom`。

### 2.1 方向缺省是 desc，不是 SQL 的 asc

SQL 的缺省是升序。如果模型漏写方向而我们跟着 SQL 缺省走，
「保费最高的 5 个区域」会返回**最低的 5 个**——数字都在，只是完全反了。
故 `Sort` 的构造器把缺失方向兜底成 `desc`，并在 prompt 里要求模型永远显式写出。
不认识的取值（如 `ascending`）直接拒绝，走重问。

## 3. 占比：`SUM(expr) OVER ()`，不另起子查询

```sql
SUM(v) / NULLIF(SUM(SUM(v)) OVER (), 0) AS `保费占比`
```

- 分母是**本次结果的总和**（窗口在聚合结果上再开一层），不是全表、也不是某一行。
- 五种库都支持聚合之上的窗口函数；换成"自连接求总和"会把行级权限谓词再复制一遍，
  多一处出错的机会。
- **脱敏传导**：占比能反推出被脱敏指标的相对分布，输入被脱敏时占比整列输出 `'***'`。

## 4. 同环比：单次扫描 + 平移分组键，不做自连接

### 4.1 方案对比

| 方案 | 问题 |
|---|---|
| 两个子查询自连接 | 权限谓词要注入两次；两个子查询的分组键是不同年份的标签（2024-03 vs 2025-03），还得再造一个相对键 |
| **单次扫描 + CASE 过滤 + 平移分组键** | 只需要一个方言方法 `addInterval` |

选后者：

```sql
SELECT DATE_FORMAT(
         CASE WHEN t.order_date < ? THEN DATE_ADD(t.order_date, INTERVAL 1 YEAR)
              ELSE t.order_date END, '%Y-%m') AS `月份`,
       SUM(CASE WHEN t.order_date >= ? AND t.order_date < ? THEN t.amount END) AS `保费`,
       SUM(CASE WHEN t.order_date >= ? AND t.order_date < ? THEN t.amount END) AS `保费上期`,
       (...) / NULLIF(..., 0) AS `保费同比`
FROM ...
WHERE ((t.order_date >= ? AND t.order_date < ?)      -- 本期
    OR (t.order_date >= ? AND t.order_date < ?))     -- 上期
GROUP BY <同一个 DATE_FORMAT 表达式>
```

关键点：**上一期的行先被平移到本期时间轴**（2024-03 → 2025-03），
两期才落在同一个分组键上。不自建相对键、不依赖数据连续性。

### 4.2 粒度限制是硬约束，不是保守

- 同比只允许 `month` / `year`：按天做同比，2 月 29 日平移一年会落到 2 月 28 日，
  与当年 2 月 28 日**撞进同一组**，增长率静默算错。
- 环比只允许 `day` / `month`。
- 没有时间维度时（如「今年保费同比」）粒度无关，语义是"本期总额 vs 上期总额"。

### 4.3 三列：本期、上期、增长率

只给增长率看不出量级（涨 300% 可能是从 1 涨到 4），只给两期又要用户自己算。
三个都出，列名为 `X` / `X上期` / `X同比|环比`。增长率是**小数**（0.15 = 15%），
与派生指标的比值口径一致。

### 4.4 实现上踩到的一个坑

维度表达式会同时出现在 `SELECT` 与 `GROUP BY` **两处**。同环比给维度加了
`CASE WHEN ... < ?`，于是同一个 `?` 也出现两次，参数必须跟着追加两次。
`RenderedSql` 的构造器会校验「占位符数 == 参数数」，所以漏掉时立刻失败，
不会带着错位的参数去执行。

## 5. 权限

- 三种能力都不新增权限面：仍然只由 DSL 里的字段决定，仍走同一个渲染器注入行列规则。
- 同环比多查的那一个时间窗**不是**新的数据范围——行级规则照样作用在该窗的行上。
- 占比、同比列各自独立参与脱敏判定。

## 6. 验收

1. Top-N：`ORDER BY <输出列> DESC LIMIT n`；SQL Server 用 `TOP n`
2. 占比分母 = 结果总和；被脱敏指标的占比整列 `***`
3. 同比：两个时间窗都进 WHERE；上一期行被平移；列数为 3×指标数
4. 粒度不合法 / 没有 timeRange 时**拒绝**，不近似
5. 评测集：新增 5 条（Top-N ×2、占比 ×2、同比 ×1），基线不下降
6. 回显「我理解成了」增加"对比"一项，用户能看到系统额外查了哪一期

## 7. 不做

- **自定义对比期**（"对比 2019 年"）：只做固定的上一年 / 上一个月。
- **条件指标**（"已解决工单数"= 先过滤再计数）：那是另一类语义原语，
  派生指标只做已有指标之间的运算。
- **按占比排序再取前 N** 的组合虽然能用（`sort.field` 取「保费占比」），
  但不在本轮验收范围内。
