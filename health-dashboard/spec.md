# 全局健康度看板

- Status: Draft
- Date: 2026-11-04
- Related: `eval/README.md`、`ModelingCoverageCheck`、`ask_audit_log`、`ask_feedback`

## 1. 要解决什么

单个域的覆盖度已经能看了（`DomainCoverageTab`），但**没有人看全局**：

| 已有 | 缺什么 |
|---|---|
| 域列表的健康度徽章 | 只看得到"数量"，看不到"哪些问题最常见" |
| 单域覆盖度详情 | 要点进每个域去看，十几个域就是十几次点击 |
| `ask_audit_log` 6401 成功 / 267 失败 | **没人看**——失败原因埋在表里 |
| `eval` 评测报告 | 是离线的，与线上真实提问无关 |

真正的问题在真实数据里（今天查的）：

```
FAILURE 267 次，按原因分组：
  79  NOT_UNDERSTOOD                                    ← 模型没理解
  35  「评论数」配置了 COUNT，不能作为维度               ← **建模缺口**
  21  筛选条件取值不是合法日期                            ← 模型填错
  16  DSL 没有可渲染的输出列                              ← **建模缺口**
  15  带时间条件但域内没有日期列                          ← **建模缺口**
  13  「平均保障年限」配置了 AVG，不能作为维度            ← **建模缺口**
```

**前 6 类里 4 类指向建模配置**，而这正是覆盖度检查能发现的东西。
两个数据源（静态检查 + 运行审计）现在互不相通。

## 2. 目标与非目标

**目标**：一页看清「哪个域建得糙、哪种失败最常见、该先修什么」。

**非目标**：
- **不做实时监控告警**。这一期是"看一眼工程状态"的页面，不是运维告警系统。
- **不自动修复**。同覆盖度页的理由：补哪条登记是业务判断。
- **不做多租户隔离**。`ask_domain` 等表没有 `tenant_id`（IAM spec §554 已记为独立工程）。
- **不做历史趋势图**。数据只有 3 周，画趋势会误导（"在下降"可能只是样本少）。

## 3. 数据源

三张表都是现成的，**不新增采集**：

| 来源 | 提供什么 | 现状 |
|---|---|---|
| `ModelingCoverageCheck`（逐域调） | 每个域的静态短板 | 已有接口 |
| `ask_audit_log` | 真实提问的成功/失败、失败原因、耗时 | 6401/267/29，跨 3 周 |
| `ask_feedback` | 用户主动报的"答错了" | 只有 2 条，样本太少 |

**为什么把 audited 失败也放进来**：静态检查只能发现"配置形态缺失"，
发现不了"模型在这种配置下实际会犯什么错"。两者的交集才是要优先修的
——比如「评论数不能作为维度」35 次，静态检查只看得出「缺双登记」，
看不出它已经造成了 35 次真实失败。

## 4. 页面设计

### 4.1 顶部：整体状态

```
┌─────────────────────────────────────────────────────────┐
│ 问数健康度                                 最近 7 天 ▾  │
├──────────┬──────────┬──────────┬──────────┬─────────────┤
│  域      │ 提问     │ 成功率   │ 待修项   │ 反馈待审    │
│  12      │ 1,204    │ 94.2%    │ 47       │ 1           │
└──────────┴──────────┴──────────┴──────────┴─────────────┘
```

成功率 = `SUCCESS / (SUCCESS + FAILURE)`。**BLOCKED 不算**——
那是权限拒绝，是正确行为，不是质量问题。

### 4.2 中部：失败原因排行（最有用的一块）

```
失败原因 TOP 6                    最近 7 天 · 267 次失败

79  ████████████████  模型没理解问题
35  ███████           字段「评论数」配了 COUNT，不能当维度   → 去修
21  ████              筛选条件取值不是合法日期
16  ███               DSL 没有可渲染的输出列                → 去修
15  ███               带时间条件但域内没有日期列            → 去修
13  ██                「平均保障年限」配了 AVG，不能当维度   → 去修
```

**「→ 去修」是关键**：能定位到配置的失败，直接给跳转链接到对应域的覆盖度页。
做不到的（如 `NOT_UNDERSTOOD`）不给链接——给了也没用。

### 4.3 底部：域健康度总表

```
域              模式    提问    成功率   覆盖度
保险分析域      建模    412     91.3%    🟡 3
工单分析域      建模    388     88.1%    🟡 3   9
AdventureWorks  建模    —       —        🟡 23  ← 没人用过
门店分析域      建模    204     97.1%    🟡 3
冒烟测试(直连)  直连    0       —        —
```

两个刻意设计：

**① 「没人用过」要高亮。** AdventureWorks 建了但零提问——
要么是没推广，要么是建完发现不好用。两种都值得知道。
而这件事**静态检查看不出来**，只有把审计数据接进来才看得见。

**② 成功率低 + 覆盖度差要同时显示。** 单看任何一个都会误判：
成功率低可能是用户乱问，覆盖度差可能没人用。

## 5. 实现

### 5.1 后端

**新增一个只读接口** `GET /admin/health/overview?days=7`：

```java
record HealthOverview(
    Summary summary,              // 域数、提问数、成功率、待修项、反馈待审
    List<FailureReason> failures, // 失败原因排行（已归类 + 可跳转的 domainId）
    List<DomainHealth> domains    // 逐域：提问数、成功率、覆盖度计数
)
```

失败原因需要**归类**：原始 `error_message` 是长文本且带具体列名，
直接排行会得到几百个"只出现一次"的条目。

归类规则（按优先级，**已用真实 267 条失败回放过**）：

| 规则 | 归入 | 实测条数 | 可跳转 |
|---|---|---|---|
| 枚举值原样 | `NOT_UNDERSTOOD` | 79 | ✗ |
| 含「不能作为维度」 | 字段角色冲突 | 52 | ✓ |
| 含「不是合法日期」 | 取值类型错误 | 30 | ✗ |
| 含「找不到可用的日期列」 | 缺时间口径 | 26 | ✓ |
| 含「没有可渲染的输出列」 | 输出列解析失败 | 16 | ✓ |
| 含 `Unknown column` / `SQL syntax` | 模型编了不存在的列 | 16 | ✓ |
| 含「Connection is not available」/「模型未配置」 | **环境问题** | 10 | ✗ |
| 含「无法解析的时间口径」/「同环比需要明确的时间范围」 | 时间口径不支持 | 8 | ✗ |
| 其余 | 其他 | 30 | ✗ |

**「环境问题」这个桶是刻意单列的**：连接池耗尽、模型密钥缺失都不是
建模问题，混进"建模缺口"里会让管理员去改配置，而真正该做的是重启服务
或补密钥。**归类错了比不归类更糟——它会把排查方向引偏。**

实测回放后 267 条落在 **9 个桶**，最大的 `NOT_UNDERSTOOD` 79 条。

**归类是这一期最容易做错的地方**：规则太细会碎片化，太粗会掩盖差异。
规则表从上表的真实数据里提炼，写测试锁住——新增一种失败模式时
应该能立刻看出它落在了哪个桶，而不是默默掉进"其他"。

### 5.2 前端

新页面 `/admin/health`，挂在管理台导航。

**不放进域列表页**：那里是"管理配置"的地方，这是"看运行状态"的地方，
两类信息混在一起会让两个任务都变慢。

## 7. 验收

1. **成功率与手算一致**：`SUCCESS / (SUCCESS + FAILURE)`，BLOCKED 不计入分母
2. **失败原因归类**：267 条归入 9 个桶（已用真实数据回放过），最大的桶是
   `NOT_UNDERSTOOD` 79 条；「环境问题」单独成桶，不与建模缺口混
3. **可定位的失败带跳转**：「不能作为维度」那 48 条能跳到对应域的覆盖度页
4. **没人用的域高亮**：AdventureWorks 显示"0 次提问"而不是空白
5. **直连域**：不做覆盖度检查（显示 —），但提问数与成功率照常统计
6. **审计表为空时不崩**：新部署的环境返回全零，不是 500

## 8. 风险

| 风险 | 应对 |
|---|---|
| 归类规则凭感觉写，与实际数据对不上 | 先从真实 267 条失败里提炼，写完用数据回放验证 |
| 成功率的定义被误解 | 页面上写明口径：`SUCCESS / (SUCCESS + FAILURE)`，BLOCKED 是权限拒绝不算失败 |
| 数据量小（3 周）导致结论不稳 | 不画趋势图；时间范围选择器默认 7 天 |
| 逐域查覆盖度拖慢页面 | 与域列表同样的取舍：域不多，逐个调可接受 |

## 9. 不做

- 实时告警 / 定时推送
- 自动修复
- 历史趋势图
- 多租户隔离
- 用户维度的使用分析（那是另一件事）
