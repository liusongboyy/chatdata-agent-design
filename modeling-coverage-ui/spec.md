# 建模覆盖度：把"域建得好不好"变成能看、能改的东西

- Status: Draft
- Date: 2026-11-03
- Related: `docs/modeling-coverage.md`、`eval/README.md`、`ModelingCoverageCheck`、
  `.scratch/roadmap/README.md`

## 1. 要解决什么

评测已经证明：**建模覆盖度是问数准确率最大的杠杆**——保险域只补三条聚合登记
（`COUNT_DISTINCT` / `AVG` / 双登记维度），基线从 74.2% 升到 83.3%，**代码一行未改**。

但「这个域建得够不够」现在**没有地方看**：

| 现状 | 问题 |
|---|---|
| `ModelingCoverageCheck` 在启动时跑 | 结果只进日志。管理员不会去翻启动日志 |
| `GET /domains/{id}/modeling-check` 早就有 | **前端零使用**（已核实：`chatdata-web` 里搜不到这个接口） |
| 建模助手能生成草稿 | 确认落库后，**不知道还缺什么** |

`ModelingCoverageCheck` 的注释自己就写清了要害：

> 管理员建完域**当场**就能看到还缺什么，那时他脑子里还有业务场景；
> 等启动日志里翻出来，通常已经过了几天。

这一页就是补上"当场看到"。

## 2. 目标与非目标

**目标**：让管理员在**建完域的当场**知道还缺什么、缺了会导致什么、改哪一列。

**非目标**：
- **不自动修复**。补哪条 AVG、给哪列加去重计数是业务判断。一键全补会造出
  「平均保费」被加到一个 ID 列上这种错误，而那比没配更糟。
- **不阻断保存**。覆盖度不足的域是**能用的**，只是某些问法会被硬凑。
  做成 ERROR 会把"多配一层"变成"存不了"，代价与收益不成比例
  （这条与 `ModelingCoverageCheck` 现有取舍一致）。
- **不做告警/推送**。这一期只解决"看得见"。

## 3. 现有能力盘点

`ModelingCoverageCheck` 已有 5 类建模相关检查（其余 10 类是加载/授权类，不在此页）：

| 检查 | 判据 | 检出什么 |
|---|---|---|
| `checkAggregations` | 有数值列但无任何 AVG | 「平均每张…」只能凑成 SUM+COUNT |
| | 有分类列但无任何 COUNT_DISTINCT | 「一共涉及多少种」只能逐项列出 |
| `checkDualRole` | 数值列既当指标又可能当条件 | 「保障年限为 10 年」没法筛 |
| `checkTimeTerms` | 有日期列但没有时间口径术语 | 「上个月」解析不出来 |
| （以上全部） | **仅对建模域（MODELED）生效** | 直连域直接返回空 |
| `checkContradictions` | 同一列的配置自相矛盾 | 别名冲突等 |
| `checkNameCollisions` | 同一物理列名出现在多张表 | 模型分不清该用哪个 |

**这些都是现成的，这一期的核心是把它显示出来 + 说人话。**

## 4. 设计

### 4.1 域详情页加「覆盖度」标签

现有 `DomainTablesView` 是注册表编辑页。加一个标签页，不是新路由——
保持"一个域的配置都在一个地方"的直觉。

```
语义域 / 保险分析域
┌─────────┬──────────────┬────────────┐
│ 注册表  │ 表间关联     │ 覆盖度 ③  │   ← ③ = 问题条数
└─────────┴──────────────┴────────────┘
```

内容按严重度分组，每条给三样东西：

```
🔴 严重（1）
  直连模式配了行列规则
  直连模式下模型自己写 SQL，规则没有安全的注入点，配了也不生效。
  但管理员会以为保护了数据——不生效的"限制"比没有更危险。
  → 要么改用建模模式，要么删掉规则

🟡 建议（3）
  域内没有 AVG 指标
  问「平均每张保单的保费」时，模型只能给 SUM 和 COUNT，用户得自己相除。
  可补的列：premium（保费）、term_years（保障年限）
  → [去注册表编辑]

  没有 COUNT_DISTINCT 指标
  ...
```

### 4.2 关键设计：每条要给「可操作的位置」

> 只说「这个域缺 AVG」等于没说。管理员需要知道**改哪一列**。

所以 `EngineConfigViolation` 要能带**定位信息**：

```java
public record Location(String table, String column, String hint) {}
```

`hint` 是简短的动作建议（`"补一条 AVG 指标"`），不是长文案——
长文案在 `message` 里，两者职责不同。

**这一期只对 `THIN_MODELING` 类加 location**，其余类别保持原样：
- 改动面小，风险低
- 其余的定位方式各不相同（授权是角色名、关联是表 id），一次性统一没有收益

### 4.3 域列表加健康度徽章

管理员打开"语义域"列表，要能一眼看出哪个域建得糙：

```
保险分析域        建模   🔴 2  🟡 5
工单分析域        建模   🟡 3
门店分析域        建模   ✓
AdventureWorks   直连   —      （直连模式不做建模检查，不显示徽章）
```

数据来源：`GET /domains/{id}/modeling-check` 逐个调。**域不多（十几个），
逐条调可以接受**；等域上百了再做批量接口——现在做是过早优化。

### 4.4 建模助手 → 覆盖度页的衔接

草稿确认落库后，现在的行为是跳回域列表。改成：

```
创建成功 → 「已创建域「销售分析域」（5 张表，79 列）」+ [查看还缺什么]
                                              ↓
                                        直接跳到覆盖度页
```

理由：建完那一刻，管理员脑子里还有业务场景（"哦对，我还需要能问平均客单价"）。
**过一小时再看，他要先回忆自己当初想配什么。**

## 5. 实施清单

| 位置 | 改动 | 说明 |
|---|---|---|
| `EngineConfigViolation` | 加 `Location` 字段（可空） | 只 `THIN_MODELING` 类填 |
| `ModelingCoverageCheck` | 5 处 `violation(...)` 调用带上 location | 需要把 `label(t,c)` 拆成 (表, 列) |
| `AdminEngineController` | `modeling-check` 返回值已含新字段，无需改 | 序列化自动带出 |
| `chatdata-web/src/api/admin.ts` | `modelingCheck(domainId)` + `Violation` 类型 | |
| `DomainTablesView.vue` | 加「覆盖度」标签页 | 主要工作量 |
| `DomainListView.vue` | 加健康度徽章 | 逐域调接口 |
| `ModelingDraftView.vue` | 成功后新增「查看还缺什么」按钮 | 一行 |

**不做**：批量检查接口、一键修复、自动定时检查。

## 6. 验收

1. **保险分析域**：打开覆盖度页，能看到当前基线暴露的问题（评测已知它缺
   `COUNT_DISTINCT` 与双登记），且每条都指向具体列
2. **门店分析域**：应该是干净的（前一轮已补过建模），显示"没有发现明显短板"
3. **直连域**：返回空列表，页面显示"直连模式不做建模检查"。
   （核实过：`ModelingCoverageCheck.check` 对 `domain.isRaw()` 直接 `return List.of()`，
   连时间口径检查也不跑——直连没有列定义，这套判据不适用）
4. **健康度徽章与实际一致**：列表上显示 ③ 的域，点进去确实是 3 条
5. **不阻断**：有 🔴 的域照样能保存、能问数——这一页只提示，不拦

## 7. 风险

| 风险 | 应对 |
|---|---|
| 建议太泛，管理员照着改反而错 | 每条给**具体列**和**为什么**；不提供一键修复 |
| 逐域调接口拖慢列表 | 十几条域 × 单次 ~50ms 可接受；上百条时再改批量 |
| 与 `eval` 的口径不一致 | 两处都用同一个 `ModelingCoverageCheck`，不另写判据 |
| 红色太多造成"告警疲劳" | 只有真正的 ERROR 用红色；建模建议一律黄色 |

## 8. 不做

- 自动修复 / 一键补全
- 保存时阻断
- 覆盖度变化的历史趋势
- 把覆盖度并入评测门禁（那是另一件事，需要先有稳定的基线）
