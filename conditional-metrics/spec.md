# 带条件的指标 + 自定义对比期

- Status: Done（2026-10-26，含 AND/OR 与字段比较）
- Date: 2026-10-26
- Related: `.scratch/derived-metrics/spec.md`、`.scratch/analytics-dsl/spec.md`

## 一、带条件的指标

### 1. 要解决什么

「已解决工单数」「有效保单数」「内部备注数」这类指标 = **先过滤再聚合**。
之前要么让模型加 filter（整条查询被过滤，分母消失），要么根本答不了。

### 2. 决定：条件挂在指标上，用 CASE 渲染，不进 WHERE

```json
{"col":"ticket_no","type":"varchar","agg":"COUNT","alias":"已解决工单数",
 "condition":{"field":"状态","op":"=","value":"RESOLVED"}}
```

渲染成：

```sql
COUNT(CASE WHEN `t1`.`status` = ? THEN `t1`.`ticket_no` END)
```

**为什么不能进 WHERE**：WHERE 会把同一条查询的所有指标一起过滤。
「已解决占比」= 已解决数 / 总工单数，进了 WHERE 分母就变成分子，结果永远是 100%，
而且不报错。

### 3. 两条配套规则

- **条件可以跨表**：条件字段可能配在维表上（状态、渠道）。渲染器把所有指标的
  条件字段所在表一并纳入 JOIN 规划，否则就是 `Unknown column t5.status`。
- **条件必须传导到派生指标**：`已解决占比` 的分子是条件指标，解析时保留条件；
  丢了条件等于分子分母口径不一致，而 SQL 照样跑得通。

### 4. 参数顺序（实现坑）

同环比的窗口 CASE 在**外层**，统计条件在**内层**：

```sql
SUM(CASE WHEN <窗口> THEN CASE WHEN <条件> THEN col END END)
```

SQL 文本里窗口占位符在前，但代码里是先构造内层再包外层，参数很容易追加反。
`ColumnWrapper` 因此做成两段式：`begin(params)` 先占参数，`apply(expr)` 再包表达式。

### 5. 取值是配置，不是用户输入

运算符只支持 `= / != / > / < / >= / <= / in / like`，取值一律走占位符。

### 5.1 AND / OR 多条件（一层）

```json
{"logic":"and","conditions":[
  {"field":"状态","op":"=","value":"RESOLVED"},
  {"field":"优先级","op":">","value":"2"}]}
```

- 单条件仍写扁平形态（`{field,op,value}`），多条件才包一层。两种形态由同一个解析器处理，
  管理台、手写配置、夹具都用同一套。
- **不做嵌套**（(A 或 B) 且 C）：需要表达式树，而真实口径里极少见；编辑器也会变得难用。
- 多个条件整体加括号，再放进 `CASE WHEN`。
- 上线限 10 项：手滑粘贴一个长列表能生成几百个占位符。

### 5.2 字段与字段比较

```json
{"field":"关闭时间","op":">","rightField":"SLA截止时间"}
```

- 两侧都是列引用，**不产生参数**；`rightField` 与 `value` 二选一。
- 只允许比较运算符。`in` / `like` 的右侧写列名没有公认语义，各库行为也不一致，直接拒绝。
- 右侧字段同样参与 JOIN 规划——否则条件里的列不在 FROM 里。
- 不做类型前置校验：我们没有可靠的类型信息，让库自己报错比猜一个转换规则安全。

### 6. 管理台

列编辑器增加「＋ 统计条件」（只在有聚合方式的列上出现）：条件字段、运算符、取值，
底部实时显示「仅统计满足「状态 = RESOLVED」的行」。保存时按运行时同一份规则校验。

## 二、自定义对比期

### 1. DSL

```json
"compare": {"mode":"custom","start":"2023-01-01","end":"2023-12-31"}
"compare": {"mode":"yoy"}          // 向后兼容 {"mode":"yoy"} 与字符串 "yoy"
```

### 2. 对齐规则（这是全部难点）

对比期与本期是两个独立时间窗。要把对比期的行平移到本期时间轴上分组，
必须能用一个**常量位移**做到：

1. 先试整月：`prevStart + k 月 == curStart` 且 `prevEnd + k 月 == curEnd`
2. 再试整天：同上，按天
3. 都不成立 → **拒绝**（有分组时）。近似对齐会把两组数据错位合并，且不报错

没有时间维度时不需要对齐，任意两段都能比（就是"本期总额 vs 对比期总额"）。

### 3. 按天分组只能用按天平移

按月/年平移会把不同的天并进同一组：1 月 31 日 + 1 个月 = 2 月 28 日，
与真实的 2 月 28 日撞组；闰年同理。故 `granularity=day` 时只允许位移单位为天的对比期。

**这同时收紧了上一轮的环比**：环比（位移 1 个月）现在要求按月分组。
上一版允许按天环比，属于同一类静默错位，本轮一并改掉。

## 三、验收

1. 条件用 CASE 渲染、不进 WHERE；条件字段跨表时 JOIN 自动补齐
2. 派生指标引用条件指标时条件不丢；条件 + 同环比时参数顺序正确
3. 自定义对比期：整月对齐 → `INTERVAL k MONTH`；对不齐 → 拒绝
4. 管理台可配、可校验，错误提示是人话
5. 评测：新增 3 条（条件指标 ×2、自定义对比 ×1），全部通过，基线不降

## 四、筛选条件也支持字段比较

「关闭时间晚于 SLA 截止时间」原本被当成日期字面量校验而失败。现在：

```json
{"field":"关闭时间","op":">","rightField":"SLA截止时间","value":null}
```

- `Filter` 增加可空的 `rightField`，与 `value` 二选一（两者都给时以 `rightField` 为准，
  因为 schema 里 `value` 仍是必填——去掉它会让模型系统性丢值）。
- 右侧字段的所在表同样纳入 JOIN 规划。
- 渲染成 `t1.closed_at > t1.sla_deadline`，无参数。

## 五、不做

- **嵌套条件**（(A 或 B) 且 C）：需要表达式树，且管理台难用。
- **条件里的函数/表达式**（`DATEDIFF(...) > 3`）：那等于把 SQL 交给配置者。
- **对比期自动推荐**（"该跟谁比"）：那是洞察层的事，不在 DSL 里猜。
- **字段比较的类型转换**：交给数据库报错，不猜。
