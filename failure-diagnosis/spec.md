# 闭环：从「发现问题」到「修好它」

- Status: Draft
- Date: 2026-11-04
- Related: `.scratch/health-dashboard/spec.md`、`.scratch/quality-analysis/spec.md`、
  `FailureClassifier`、`ModelingDraftView`

## 1. 要解决什么

前两轮做了「看见问题」：

| 已有 | 能回答 |
|---|---|
| 建模覆盖度 | 这个域**缺什么配置** |
| 健康度看板 | 整体成功率、失败原因排行 |
| 质量分析 | **哪类问题**在拖后腿 |

但**看见之后还得自己找路去修**。以真实案例为例：

```
质量分析 →「单值汇总」→ 发现「平均优先级是多少？」22 次全失败
  ↓ 然后呢？
  要自己去查审计表看 error_message
  ↓
  发现是 NOT_UNDERSTOOD
  ↓
  要打开域注册表找「优先级」这列
  ↓
  发现已经配了 平均优先级 AVG(int)
  ↓
  配置是对的 —— 那是模型能力问题，改配置没用
```

**这一路的每一步都要人自己拼。** 而拼错的代价是：去改了不需要改的配置。

## 2. 核心洞察：不是所有失败都能靠改配置解决

这是这一期最重要的判断。实测的真实案例：

| 失败 | 表面看 | 实际原因 | 该做什么 |
|---|---|---|---|
| 「平均优先级是多少」22 次 | 建模问题？ | `NOT_UNDERSTOOD`，而「平均优先级 AVG」**已经配对了** | **什么也做不了**——模型能力边界 |
| 「评论数不能作为维度」52 次 | 建模问题 | 确实缺双登记 | 补一条维度 |
| 「Connection is not available」10 次 | 连接失败 | 连接池耗尽 | 重启服务 |

**如果把「改配置」当成万能解，会让管理员在第三类上空转。**
所以闭环的第一步不是"给修复建议"，而是**判断能不能修**。

## 3. 设计

### 3.1 每个失败原因分三档

在 `FailureClassifier` 现有的 `fixable` 布尔值上扩展成三档：

```java
enum Fixability {
    /** 改建模配置能解决，且知道改哪 */
    CONFIG,
    /** 改配置也解决不了：模型能力边界、用户提问方式 */
    NOT_CONFIG,
    /** 环境问题：重启服务、补密钥 */
    ENVIRONMENT
}
```

现有 `fixable` 二元判断太粗——`NOT_CONFIG` 和 `ENVIRONMENT` 都返回 false，
但两者的下一步动作完全不同（一个是"没办法"，一个是"去重启"）。

### 3.2 能修的要能直接跳到「改哪」

质量分析页的每个问法、健康度的每个失败桶，如果 `Fixability.CONFIG`，
给一个跳转：

```
平均优先级是多少？  22 次  100% 失败  [查配置 →]
                    ↓ 点击
域「工单分析域」的注册表，定位到「优先级」那一列
```

**定位到列而不是只到域**：域里有几十列，跳过去还要再找一遍。

### 3.3 不能修的要说清「为什么」

这是比给建议更重要的事。用户看到 100% 失败会本能地去改配置，
而有些情况下**改了也没用**——不说清就是在浪费他的时间。

```
平均优先级是多少？  22 次  100% 失败
  原因：模型没能把这个问题翻译成查询（NOT_UNDERSTOOD）
  检查过：「平均优先级」这个指标已经配好了（AVG，int）
  → 这是模型能力边界，改建模配置解决不了。
    可以试试换一种问法，或调整提问方式。
```

**「检查过」那句话是关键**：它证明系统真的去看了配置，
而不是甩一句"模型没理解"就走。而"已经配好了"这个结论需要**反查注册表**。

### 3.4 反查逻辑

给定一个失败 + 域，判断配置是否已经存在：

| 失败类型 | 反查什么 | 结论 |
|---|---|---|
| `NOT_UNDERSTOOD` | 问题里的关键词能否匹配到已注册字段的别名 | 能匹配 → 配置已有，问题在模型<br>完全匹配不到 → **可能问错了域**，见下 |
| `ROLE_CONFLICT` | 该列是否有维度那条 | 没有 → 补双登记（可修） |
| `NO_TIME_COLUMN` | 域内是否有日期列 | 没有 → 加日期列别名（可修） |
| `NO_OUTPUT_COLUMN` | 指标是否配了聚合 | 没有 → 补聚合（可修） |

**这个反查是纯函数**：输入（问题、失败原因、域的字段清单），输出（结论 + 定位）。
可单测，不需要查库。

#### 实测：反查能给出有价值的结论

三类真实失败，反查后的结论各不相同：

| 真实失败 | 反查结果 | 结论 |
|---|---|---|
| 「客户总数是多少」20 次 | 域里有「客户数」 | 配置已有（名称略不同），问题在模型选字段 |
| 「各门店的订单金额合计」12 次 | 落在**保险域**，该域无任何门店字段 | **问错了域** |
| 「平均优先级是多少」22 次 | 域里有「平均优先级 AVG(int)」 | 配置完全正确，模型能力边界 |

**第二类是这一期最有价值的产出**：用户以为问数是坏的，
实际是这句问题本来就该走门店域。系统能直接告诉他"这个域里没有门店相关的字段"。

#### 匹配必须模糊

实测：「客户总数」匹配不到「客户数」——精确匹配会漏掉它。
所以用**子串包含**：问题的任一片段被某个别名包含、或别名被问题包含，都算命中。

这会把「今天上海的天气怎么样」也碰巧匹配到含"上海"的字段——
所以**置信度分档是必需的**，不能只看匹没匹配上（见 §3.5）。

### 3.5 一个必须承认的局限

**关键词匹配会很粗糙。** 「平均优先级」能匹配到「优先级」，但「客户总数」
和「客户数量」是两个不同的别名，匹配会失败。

所以反查的结论要分三档置信度：

- **确定**：精确匹配到了字段别名
- **可能**：部分匹配（含相同子串）
- **无法判断**：完全匹配不上

**「无法判断」时不假装有答案** —— 说"没找到相关字段，可能需要补充术语或调整问法"，
而不是硬给一个"可修"的结论让人去改一堆东西。

## 4. 页面改动

### 4.1 质量分析页

每个低频失败问法后面加一列「诊断」：

```
问法                          次数  失败率  诊断
平均优先级是多少？              22   100%   模型能力边界 ▸
评论数最多的工单？              35    100%   缺双登记 [去修 →]
```

点「▸」展开诊断详情（见 §3.3 的文案）。

### 4.2 健康度页

失败桶的「去修」链接现在指向 `/admin/health`（等于没跳）。改成：

- `Fixability.CONFIG` + 能定位到域 → 跳到那个域的覆盖度页
- `Fixability.ENVIRONMENT` → 不跳，文案写"需要重启服务或补密钥"
- `Fixability.NOT_CONFIG` → 不跳，文案写"改配置解决不了"

## 5. 实施清单

| 位置 | 改动 |
|---|---|
| `FailureClassifier` | `fixable:boolean` → `Fixability` 三档 |
| `FailureDiagnosis`（新） | 纯函数：失败 + 域字段清单 → 诊断结论 + 定位 + 置信度 |
| `HealthService` | 失败桶带上诊断 |
| `QualityReport` | 每个问法带上诊断 |
| `QualityPanel.vue` | 加「诊断」列 + 展开详情 |
| `HealthView.vue` | 「去修」链接真正跳转 |
| `DomainTablesView.vue` | 支持 `?highlight=列名` 参数，高亮定位到那一列 |

## 6. 验收

1. **「平均优先级是多少」**：诊断为「模型能力边界」，并显示"检查过：已配 AVG"
2. **「评论数不能作为维度」**：诊断为「缺双登记」，点「去修」跳到该域注册表并高亮那一列
3. **环境问题**：不显示「去修」，文案说"需要重启服务"
4. **匹配不上的问题**：说"没找到相关字段"而不是硬给建议
5. **诊断不影响原有统计**：类型分布、失败率不变

## 7. 风险

| 风险 | 应对 |
|---|---|
| **关键词反查不可靠，给出错误结论** | 三档置信度；「无法判断」时不给建议 |
| 诊断结论过期（配置已经改过） | 诊断是**实时计算**的，每次都基于当前配置 |
| 用户以为「模型能力边界」是甩锅 | 附上"检查过 X 已配置"的证据，证明真的看了 |
| 跳转定位到列在长表里找不到 | 高亮 + 滚动到该行 |

## 8. 不做

- 自动改配置（补哪条是业务判断，同前几期）
- 失败原因的模型侧分析（那是模型团队的事）
- 跨域的诊断聚合（诊断是单域内的判断）
