# Roadmap：从「能问」到「会用」

- Status: Active
- Date: 2026-11-03
- Related: `.scratch/modeling-assistant/spec.md`、`.scratch/feishu-channel/spec.md`、

## 0. 为什么现在写这个

三个入口（浏览器 / 飞书 / A2A）加 agentscope 管理台都通了，底座完整。
继续铺入口的边际收益在下降，该往「让人用得起来、用得下去」走。

这份 roadmap 的排序依据不是「哪个功能酷」，是**项目自己暴露出来的证据**：
评测失败用例、spec 里标了未实现的、以及管理台里重复出现的操作。

## 1. 现状盘点

| 维度 | 状态 |
|---|---|
| 核心 | 语义模型 → DSL → SQL 渲染，权限在渲染器固定注入（ADR-0002） |
| 入口 | 网关 BFF、飞书 webhook、A2A（mesh）、agentscope 管理台（aistio） |

**结论**：能力不缺，缺的是「降低使用门槛」和「从被动回答到主动发现」。

## 2. 阶段一：填平已知的坑（1–2 周）

### 2.1 建模助手（P0 后端 + API）

**依据**：`.scratch/modeling-assistant/spec.md`（设计完成，未实现）

评测已经证明**建模覆盖度是准确率最大的杠杆**——保险域只补三条聚合登记，
基线从 74.2% 升到 83.3%，代码一行未改。

但建模极贵：AdventureWorks 28 表 / 172 列 / 30 关联是手工写的，花了大半天。
**最大的杠杆挂着最高的使用成本**，这是当前最矛盾的地方。

**范围（P0）**：
- `ColumnInferrer`：列 + 基数 → 角色 / 聚合 / 置信度 / 理由（纯函数，可单测）
- `JoinInferrer`：外键 + 命名 → 关联候选（本仓库 AdventureWorks 库一条外键都没有，
  命名推断不能省）
- `SensitiveColumns`：敏感列名单，**默认关闭**（漏关一个 = 数据泄露）
- `POST /datasources/{id}/modeling-draft`：返回草稿，**不落库**
- 草稿内嵌 `ModelingCoverageCheck` 结果

**不做**：自动建域、生成业务别名（只给候选标「待确认」）、推断派生/条件指标、
猜 `base_filter`。理由见 spec §2。

**验收**：AdventureWorks 五张表生成的草稿里，金额列有 SUM+AVG、状态列有
COUNT_DISTINCT、日期列被识别、三个外键关系被推断；覆盖度警告从 22 条降到接近 0。

### 2.2 飞书定时推送

**依据**：`feishu-channel/spec.md:747`「仍未实现：定时推送」

现在只能在有人问的时候答。**「每天早上 9 点把昨天各门店销售额发到群里」
是业务方最常见的诉求**，而现在做不到。

**范围**：
- `channel_subscription` 表：`(channel, chat_key, question, cron, enabled, created_by)`
- 调度器按 cron 触发 → 走完整换令牌链路 → 用该订阅创建人的身份查数
- **权限仍按创建人判**：订阅不是后门，换了人看同一个订阅，数据范围还是他自己的

**关键决策**：推送用**谁的令牌**
- 选「订阅创建人」：范围与创建人一致，安全
- 不选「机器人自己」：那是越权，且审计里看不出是谁要的数据

**验收**：配一条 `0 0 9 * * ?` 的订阅，第二天 9 点群里收到卡片；
创建人权限被收回后，推送在发送前被拒并记审计。

### 2.3 飞书占位卡片原地更新

**依据**：`feishu-channel/spec.md:747`

问数要几秒到十几秒。现在的做法是先发「正在查询」再发结果——**两条消息**。
用户看到的是聊天记录被撑开，而不是「这条卡片变了」。

**范围**：用 `message_id` 走飞书 `PATCH /im/v1/messages/{message_id}` 更新原卡片。

**风险**：飞书对卡片更新的频率和体积有限制。要实测：更新间隔 < 1s 时是否被限流。

## 3. 阶段二：从「问」到「主动发现」（3–4 周）

这是我认为**最有杠杆**的方向，也是把现有能力用到位。

| | 现在 | 应该 |
|---|---|---|
| 触发 | 人问 | 指标异动时机器主动说 |
| 分析 | `analysis/` 包（拆解 → 执行 → 洞察）已有 | 挂到定时任务，异动才推送 |
| 通道 | 飞书 webhook 被动接收 | agentscope `Automations` 或自建调度 |

**为什么现在能做**：`InsightCalculator` 26KB、`AnalysisExecutor` 已有，
洞察逻辑做得很深。缺的只是「定期自己跑、发现异常才说」这一层。

**待定（必须先回答再写 spec）**：监控什么？
- 阈值型（销售额跌 20%）—— 实现简单，误报多
- 统计型（连续三天低于均值 2σ）—— 需要历史基线
- 模型判断型（让 LLM 看数据说有没有异常）—— 贵且不稳定

这三种架构完全不同，**不先定就是白做**。

## 4. 阶段三：让 agent 能动手（4–8 周，暂缓）

你提过「直接帮忙操作业务系统」。方向上成立，但：

| 前提 | 状态 |
|---|---|
| 预览 → 确认 → 执行 → 可回滚 | 未设计 |
| 事务边界与失败补偿 | 未设计 |
| 写操作的审计与追责 | 未设计 |

**读错了顶多看错数字，写错了是事故。** 这一层要先把上面三件事设计清楚，
不列入近期排期。

## 5. 本次要做的三项

| # | 事项 | 依据 | 预估 |
|---|---|---|---|
| 1 | 建模助手（P0 后端） | spec 已完成，评测证明高杠杆 | 3–5 天 |
| 2 | 飞书定时推送 | spec 明列未实现，业务方高频诉求 | 2–3 天 |
| 3 | 飞书占位卡片原地更新 | spec 明列未实现，体验硬伤 | 0.5–1 天 |

**曾列入但已核实不成立**：`eval/README.md` 提到的「DSL 没有空值判断」——
实际 `AskSqlRenderer:1171` 早已支持（含中文写法），`AnalyticsDslRenderTest:169`
有测试覆盖。那段是历史记录，描述当时的修复过程，不是待办。

## 6. 判断依据：为什么是这三项

三条共同点：
- **有明确证据**（spec 或评测写着的），不是拍脑袋
- **不引入新架构**（建模助手复用现有写接口，推送复用现有换令牌链路）
- **做完立刻可验证**（草稿 vs 手工配置的覆盖率差距、第二天 9 点有没有收到卡片）

而阶段二的「主动监控」虽然有价值，但**缺口头问题没答**（监控什么），
现在做就是返工。

## 7. 排序原则（供后续复用）

1. 有 spec 且已验证的 > 有 spec 未验证的 > 只有想法的
2. 降低使用门槛的 > 增加功能的
3. 失败方向安全的 > 失败方向危险的（敏感列默认关闭、草稿不落库都是这个原则）
4. 能立刻验证的 > 需要长期观察的
